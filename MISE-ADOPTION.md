## First use

1. Install an approved, verified, exact mise release once on your workstation.
2. Read `mise.toml` before trusting it. Repository configuration and tasks can execute code.
3. Run `mise trust` in this repository only after review.
4. Run `mise install --locked` to download the declared tools.
5. Run `mise run toolchain` to inspect versions. Success proves version availability, not application correctness.
6. Follow this repository's existing dependency setup in an isolated environment. mise does not replace Python requirements, npm package locks, Terraform provider locks, system packages, or database services.
7. Run the existing repository tests and required CI checks. Do not rename required check contexts or enable deployment as part of installation.
8. The supplied `mise.lock` was generated by mise 2026.10.25 for Linux x64 and installed successfully. Additional platforms require generated locks and validation before support is claimed.
9. Migrate CI in a separate reviewed change using the same configuration. Pin the mise installer action to a reviewed full commit SHA and the mise binary to an exact version; retain all existing gates and permissions.

## Boundaries

## Pilot: repository-level bounds (added 2026-11-03, ADR-0010 M-01 and M-02)

Two files that the original proposal did not carry, and the reason each exists:

- `.miserc.toml` sets `ceiling_paths` so mise stops searching parent directories
  above this repository. mise loads config from the filesystem root down to the
  current directory and merges `[tools]` per tool, so without a bound a stray
  `../mise.toml` silently adds tools here that CI never sees. It must live in
  `.miserc.toml`, not in `[settings]` in `mise.toml`, because mise reads the
  former before any `mise.toml`. The ceiling names the **parent** of the
  repository root: a ceiling directory is not searched itself, so pointing it at
  this directory would disable the config it is meant to protect.
- `mise.toml` gains `[tool_config] locked = true`, which makes strict lockfile
  mode a property of the repository rather than of one CI invocation.
  `install_args: --locked` in the workflow bound the job; a developer running
  plain `mise install` was never bound by it.

### What is proven, and by what

`mise-config-scope`, the second job in `.github/workflows/mise-toolchain.yml`, is a
refusal test with four legs. Each negative leg is paired with a positive one,
because a guard that only asserts absence also passes when the command printed
nothing:

1. With `MISE_CEILING_PATHS=""`, `mise config` **must** list a decoy planted one
   directory above the checkout. This proves the decoy is discoverable, so leg 2
   is not vacuous.
2. With the committed `.miserc.toml`, `mise config` must **not** list the decoy and
   must still list this repository's `mise.toml`.
3. Plain `mise install`, no `--locked` flag anywhere, must succeed from the
   committed lockfile.
4. The same plain `mise install`, against a copy whose `python` request is changed
   to `3.12.15` (a real release, not the locked one), must be refused with a
   lockfile reason.

### Limits this pilot does not remove

- `ceiling_paths` **fails open**. If the Tera template does not render, mise uses
  the file's raw content as a literal path, that path matches nothing, discovery
  stays unbounded, and no warning is printed because the file is read before
  logging starts. Leg 2 is what turns that declaration into a control; deleting
  the leg deletes the control.
- A project `.miserc.toml` **cannot** ignore global or system config.
  `~/.config/mise/config.toml` and `/etc/mise` still merge into every project on
  the machine, and `env` is empty in a project miserc so this file cannot even
  read the environment to compensate. The remaining half of the bound is a
  machine baseline (ADR-0010 M-04) and nothing in this repository enforces it.
- Both bounds are exercised on **Linux x64 only**, in CI, on a hosted runner with
  `permissions: contents: read` and no secrets. Workstation behaviour is untested
  here because mise is not installed on the operator's host and installing it
  requires an approved, digest-pinned source that is not yet recorded.
- The other sixteen repositories carry neither file. This branch is a pilot; it is
  not a fleet state.

### Measured result of the four legs (run 41669118323, job 126032389384, 2026-11-03)

All four printed their verdict; the job is not green on assertion count, it is
green on the output quoted below. `mise config` abbreviates the home directory, so
`~/work/jolarca-control/mise.toml` is the decoy and
`~/work/jolarca-control/jolarca-control/mise.toml` is this repository.

- **Leg 1, `MISE_CEILING_PATHS=""`** — mise listed the decoy and adopted its tool:
  `~/work/jolarca-control/mise.toml  bidi-decoy`. mise's parent-directory
  inheritance is therefore demonstrated on this runner, not assumed, which is what
  makes leg 2 a test rather than a tautology.
- **Leg 2, committed `.miserc.toml`** — the decoy is absent and the pins mise
  actually selects are still this repository's:
  `python 3.12.16 ~/work/jolarca-control/jolarca-control/mise.toml` and
  `terraform 1.16.1 …`. Because an unrendered template would leave the literal
  string as a path matching nothing (fail-open, silently), this leg is also the
  proof that `{{ config_root | dirname }}` rendered.
- **Leg 3** — `mise install` with no `--locked` flag anywhere succeeded from the
  committed lockfile.
- **Leg 4** — `mise install python` against a scratch copy requesting
  `python@3.12.15`, a real release absent from `mise.lock`, refused:
  `failed: python@3.12.15 is not in the lockfile` /
  `hint: Run 'mise lock' to update the lockfile, or disable 'tool_config.locked'`.
  The refusal names the mechanism, so the guard's `lock` match is attributable to
  the fixture rather than incidental. Resolution took 0 ms: nothing was downloaded,
  which is why the whole job runs in seconds.

Two incidental facts worth recording because they change how the job must be
written: mise prints config paths with `~` substituted for `HOME`, so a guard that
greps for `$GITHUB_WORKSPACE/...` matches nothing while the config it seeks **is**
loaded — that exact bug made this job fail on its first run and its failure output
was the proof of the inheritance; and `jdx/mise-action` exports
`MISE_TRUSTED_CONFIG_PATHS` for the workspace plus `MISE_YES=1`, so the action
trusts the checked-out configuration for its own steps. The second is the
fork-PR trust question ADR-0010 raises for self-hosted runners; it is tolerable
here only because this job has `permissions: contents: read`, no secrets and no
deployment path.

## Two first attempts at this job failed, and what each taught

1. Four steps used a shell fallback to keep reading after a command failed.
   `tests/test_ci_gates_are_real.py::test_no_run_step_swallows_its_exit_status`
   forbids that token in any `run:` step and named all four. The rule is the
   executable form of AGENTS.md section 3: handing a verdict to a fallback reports
   an unreadable input as a clean scan. Every step now tests status with `if` and
   exits 1 when it cannot read its own input.
2. The decoy assertion matched on a path spelling mise does not print, so leg 1
   failed while the decoy was in fact loaded. A guard that cannot see the thing it
   is looking for must fail, and it did — which is the only reason this was caught
   before it could be believed.

Neither failure is recorded as resolved by the green badge on the second attempt;
the quoted output above is the evidence.
